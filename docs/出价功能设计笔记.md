## 1. Pull Payment 的三次实践

出价市场和挂单市场最大的区别：**钱先躺在合约里**。挂单时钱在买家手上，只在成交那一瞬间过一下合约；出价时 `msg.value` 真金白银进了合约代管（`SimpleMarket.sol` L167-171 的设计说明），一直待到成交 / 撤回 / 被拒绝。

合约一持有资金，就必然要面对"怎么把钱还回去"。本合约的解法统一为 Pull Payment，具体体现在三个地方。

### ① 成交只清被接受的那一笔，其他买家自己取回

- `acceptOffer()`：`SimpleMarket.sol` L622
- 清空动作发生在 L654（`offer.amount = 0`），随后 L658 调用 `_settleSale()`（L698）完成分账
- 设计说明原文在 L619-620：*"成交后【只清掉被接受的这一笔】，其他出价者的钱留在合约里等他们自己取回。刻意不做批量退款：一次循环里只要有一个人拒收，整笔成交就会被卡死。"*

注意清空的粒度是 `_offers[nft][tokenId][bidder]`（L237，按买家分桶），**只动被接受的那一个 bidder 的桶**，其他桶一个字节都不碰。

**为什么拒绝"批量退款"**：如果成交时顺手把所有落选出价都退回去，那这笔成交的成功与否就不再取决于买卖双方，而是取决于"所有落选者里有没有一个拒收 ETH 的合约"。一个无关的第三方地址，只要出价一次并拒收，就能永久卡死这枚 NFT 的任何成交 —— 卖家的资产处置权被外部地址劫持。宁可让落选买家多调一次 `withdrawOffer()`，也不能把成交权交到别人手上。

**踩过的坑**：一开始想的是"只保留最高价"这种更常见的出价表结构。但它天然要求"有人加价 → 给上一位退款"，也就是每一次加价都是一次 push 调用，DoS 面比批量退款还大。改成按买家分桶 + 重复出价累加（L531 `offer.amount += msg.value`）之后，出价路径上彻底没有 push，才把这块风险降为零。

对应测试：`test/SimpleMarket.test.js` L1546「【不清退他人】成交只清被接受的那一笔，落选买家的钱留在合约等自取」—— buyer 出 0.8 被接受、other 出 0.5 落选，断言 `getOffer(other) == 0.5 ETH`、`合约余额 == 0.5 + fee`，随后 other 自己 `withdrawOffer` 取回，余额降到只剩 `fee`。

### ② rejectOffer 退款失败 → 转入待领池，绝不 revert

- `rejectOffer()`：L582
- 尝试原路退回：L599 `(bool ok, ) = payable(bidder).call{value: amount}("")`
- 失败不 revert，改记账：L602 `pendingWithdrawals[bidder] += amount;` + L603 `emit RefundPending`
- 无论成功失败都发事件：L606 `emit OfferRejected(..., ok)`，`ok` 这个布尔值就是给链下看的"这笔钱退到了没有"
- 待领池声明：L243 `mapping(address => uint256) public pendingWithdrawals`

**为什么这么设计**：如果退回失败就让整笔交易回滚，那么任何人只要用一个拒收 ETH 的合约对某枚 NFT 出价一次，持有者就**永远无法拒绝任何出价**。这就是教科书级的 DoS —— 不是钱丢了，而是功能被锁死。Pull Payment 的本质就是：**把"我能不能收到钱"和"别人的操作能不能成功"彻底解耦**。

**踩过的坑（对照很关键）**：同样是"退款失败"，`withdrawOffer()`（L544）在 L558-559 是**直接 revert EthTransferFailed** 的。两者看似矛盾，其实判据只有一条 —— **调用者是不是收款人本人**：

- `withdrawOffer`：调用者 = 收款人，他拒收 → 整笔回滚 → 钱仍记在他的出价里（L554 的清零被回滚），随时可以再试一次，零损失，也就不需要额外的待领池状态；
- `rejectOffer`：调用者 = 持有者，收款人是**第三方**，第三方拒收 → 不能让持有者陪着一起失败。

测试 `SimpleMarket.test.js` L1368 把这条差异钉死了：拒收合约自己调 `withdrawOffer()` 会 revert，且 revert 之后 `getOffer` 仍然是 0.5 ETH、合约余额仍然是 0.5 ETH —— "先改状态再转账"没有把钱吃掉。

### ③ withdrawPendingFunds 自取

- `withdrawPendingFunds()`：L666
- L667 读余额 → L670 先清零 → L672 用 `call` 转出 → 失败才 revert `EthTransferFailed`（此时收款人就是 msg.sender，回滚无损失）
- 空池取款 revert `NothingToWithdraw`（L668）

测试 L1382 覆盖了完整三段链路：被拒收 → 钱进待领池（0.5 ETH）→ 仍拒收时 `claimPending()` revert 且账上金额不变 → `setRejectEth(false)` 改过自新 → 领回全额并触发 `PendingWithdrawn`，待领池归零、合约余额归零。L1407 覆盖空池 `NothingToWithdraw`。

**顺带一提，Pull Payment 在本合约还有另外两处**，不是出价功能独有，但共同构成了"合约从不主动 push 钱给无关方"的整体风格：

- 平台费：L712 `accumulatedFees += fee`（只入账不转账），owner 走 `withdrawFees()`（L881）提取；
- 创作者版税：L718 `pendingRoyalties[royaltyReceiver] += royalty`，收款人走 `withdrawRoyalties()`（L852）提取。

这让 `_settleSale()`（L698，全合约唯一动钱动 NFT 的地方）里**一次 push 都没有**：钱只从"代管桶"搬到"待领桶"，真正出合约的动作只发生在"本人主动来取"的时候。

## 2. 防 DoS 设计

### 核心判断：rejectOffer 为什么单笔退款失败不 revert

`SimpleMarket.sol` L570-577 的注释写得很直白：

> 如果退回失败就让整笔交易回滚，那么任何人只要用一个拒收 ETH 的合约对某枚 NFT 出价，就能让持有者永远无法拒绝任何出价 —— 持有者的资产处置权被一个无关地址劫持，这就是 DoS。

配套的两个设计选择：

1. **退回失败后钱不消失**：转入 `pendingWithdrawals[bidder]`，事件 `RefundPending` 让链下能订阅到"你有钱没领"；
2. **`rejectOffer` 不校验 `targetOwner`**（L576-579）：NFT 易主后新持有者拒绝一笔陈旧出价，效果是帮买家把钱退回去，对所有人都没坏处，没有理由禁止。

### 恶意合约的覆盖矩阵

| 恶意合约 | 定义位置 | 被哪个用例用到 | 测试断言了什么 |
|---|---|---|---|
| `RejectingOfferBidder`（拒收 ETH 的出价者，带 `rejectEth` 开关 + 重入探针） | `MaliciousActors.sol` L499 | L1350 / L1368 / L1382 / L1569 / L1618 / L1652 | `rejectOffer` 成功、`OfferRejected(..., false)`、`RefundPending`、待领池 == 0.5 ETH、合约余额 == 0.5 ETH |
| `ReenteringOfferBidder`（在 `onERC721Received` 里重入 `acceptOffer`） | `MaliciousActors.sol` L600 | L1589 | 重入失败且 revertData == `ReentrancyGuardReentrantCall()` 选择器；外层成交照常（`Sold` 事件、NFT 到手） |
| `RefundRejectingBuyer`（拒收 buy 多付的退款） | `MaliciousActors.sol` L152 | L475（挂单路径对照组） | 整笔回滚：NFT 不转移、挂单仍有效、买家没收到 NFT |
| `EthRejectingReceiver`（拒收一切 ETH 的收款地址） | `MaliciousActors.sol` L213 | L754（`withdrawFees` 打款分支） | revert `EthTransferFailed`，且 **`accumulatedFees` 未被清零**（原子性：钱还在市场账上，换地址还能再取） |
| `RoyaltyRejectingReceiver`（拒收版税） | `MaliciousActors.sol` L419 | L1126 | 成交照常完成，只有它自己 `withdrawRoyalties()` 时失败 |

几个值得一提的断言细节：

- **L1350 是本节的灵魂用例**：断言的是"持有者的拒绝操作必须成功"。`await market.connect(seller).rejectOffer(...)` 这一行没有包在 `expect(...).to.be.reverted` 里 —— 它必须**正常返回**，这才是防 DoS 的证明。
- **L1569「恶意出价者不阻塞成交」**：`RejectingOfferBidder` 对 #1 出价 0.8 并被接受，断言 `ownerOf(1) == bidderAddr`、`bidder.gotNft() == true`、`accumulatedFees == fee`、合约余额 == `fee`。成交时钱是打给**卖家**的，买家只收 NFT，所以它拒收 ETH 完全不影响成交 —— 这条用例顺带证明了"出价路径上没有任何一笔 push 打给买家"。
- **L1618 把 DoS 防护和重入防护串在一条链路上**：mock 的 `receive()` 在收钱瞬间同时重入 `withdrawOffer` 和 `withdrawPendingFunds`，两个都期望被锁挡下，最后断言合约余额归零、mock 手里实打实拿到 `2 × 0.5 ETH` —— 一次便宜都没占到。

**踩过的坑**：写 `RefundRejectingBuyer` 时发现，如果 mock 不正确实现 `onERC721Received`（不返回正确 selector），交易会在 `safeTransferFrom` 那一步就失败，**根本走不到退款分支**，测的就不是想测的东西。这类 mock 的"前置条件正确性"比攻击逻辑本身更容易写错。

## 3. nonReentrant 的取舍

判据不是"有没有外部调用"，而是 **"用的是 CALL 还是 STATICCALL"**（`SimpleMarket.sol` L515 原文）。

### makeOffer 不加锁

`makeOffer()`：L522，函数签名里没有 `nonReentrant`，这是刻意的，注释在 L509-515。

它内部唯一的外部调用在 L529：

```solidity
offer.targetOwner = IERC721(nftContract).ownerOf(tokenId);
```

`ownerOf` 在 `IERC721` 接口里声明为 `view`，Solidity 编译成 **STATICCALL**：被调用方禁止改状态、禁止转账，也就没法回头调用本合约的任何写函数。重入面为零，加锁纯属浪费 gas。

### withdrawOffer / rejectOffer / withdrawPendingFunds / acceptOffer 加锁

这四个函数体内都要**转 ETH 或转 NFT**，用的是 CALL，对方能在 `receive()` / `onERC721Received()` 里回来：

| 函数 | 行号 | 触发重入的外部调用 | 锁 |
|---|---|---|---|
| `withdrawOffer` | L544 | L558 `payable(msg.sender).call{value: amount}` | `nonReentrant` |
| `rejectOffer` | L582 | L599 `payable(bidder).call{value: amount}` | `nonReentrant` |
| `acceptOffer` | L622 | L658 → `_settleSale` 内的 L723 `safeTransferFrom`、L726 `payable(seller).call` | `nonReentrant` |
| `withdrawPendingFunds` | L666 | L672 `payable(msg.sender).call{value: amount}` | `nonReentrant` |

**一个容易忽略的细节**：`acceptOffer` 的锁不只挡 `acceptOffer` 自己。`ReenteringOfferBidder` 在 `onERC721Received`（`MaliciousActors.sol` L625）里连续低级 call 重入 `acceptOffer`（L630-641）和 `rejectOffer`（L644-655），而此刻它已经是 NFT 的持有者了（`ownerOf` 在 `safeTransferFrom` 内部就已更新），**身份检查本来是过得去的** —— 挡住它的只可能是那把锁。测试 L1612-1615 断言两次重入的 revertData 都等于 `ReentrancyGuardReentrantCall()` 选择器，等于把"锁真的在工作"这件事钉死了，而不是"碰巧因为别的检查失败"。

### _settleSale 本身不加锁

`_settleSale()`（L698）是 `buy()`（L479）和 `acceptOffer()`（L658）共用的结算主干。它**没有** `nonReentrant`：调用方都已经上锁，这里再加一层会因为嵌套检测直接 revert（合约注释 L693-695）。它的安全性来自"调用方已完成 Effects" —— 进入本函数时挂单 / 出价状态都已被清掉。

**踩过的坑**：

1. **给 `makeOffer` 加过锁，又撤了。** 一开始为了"看起来对称"给所有写函数都加了 `nonReentrant`。结果 solidity-coverage 会为修饰符的 `_status == _ENTERED` 分支生成覆盖统计，而一个没有重入面的函数，这个分支**永远跑不到**，覆盖率出现一块补不上的缺口。既多花了 gas，又制造了不可覆盖的死分支 —— 后来才定下"看 CALL 还是 STATICCALL"这条判据。
2. **共用结算函数时不能两头加锁。** 把分账逻辑抽成 `_settleSale` 之后，如果它自己也带 `nonReentrant`，`buy()` → `_settleSale()` 会因为重入保护的嵌套检测直接 revert。所以只在 public 入口上锁，内部函数靠"调用方已完成 Effects"来保证安全。

## 4. 资金守恒等式

### 等式本身

```
合约余额 = 代管出价 + 待领池 + 累计平台费 + 累计版税
```

- 单元测试口径（新部署合约，基线为 0）：`SimpleMarket.test.js` L1652「【资金守恒】」，核心断言 L1675-1677：

  ```js
  expect(await ethers.provider.getBalance(marketAddr)).to.equal(
    escrow + pending + fees + royalties
  );
  ```

  场景是"两笔并存出价 + 一笔拒收进池 + 接受其中一笔"，最后把该退的都退完，断言余额恰好等于 `fees + royalties`（L1687）—— 一 wei 都没被吞掉。

- 演练脚本口径（复用链上旧合约）：`scripts/practice-offer.js` L483 的 `conservation(title)`，四项全部**从链上现读**，不靠脚本自己记账（L452-453 注释："这样才叫校验"）：
  - 代管：遍历 `liveOffers` 现读 `getOffer`（L488-495）
  - 待领池：`pendingWithdrawals(addr) - baseline`（L496-504）
  - 平台费：`accumulatedFees() - feesBaseline`（L505-507）
  - 版税：`pendingRoyalties(addr) - baseline`（L508-515）

  不相等就 `throw`（L526-530），脚本 `exitCode = 1`。

### 实测拆解（成交价 0.0015 ETH）

脚本常量在 L83-87：`OFFER_A_FIRST = 0.001`、`OFFER_A_ADD = 0.0005`（A 累计 **0.0015**）、`OFFER_B = 0.002`、`OFFER_C = 0.0015`、`OFFER_D = 0.001`、`OFFER_B_HANGING = 0.001`。

| 项 | 金额（ETH） | 来源 |
|---|---|---|
| 成交价（A 累计出价） | 0.0015 | 0.001 + 0.0005 |
| 平台费 2.5% | 0.0000375 | 留在合约，等 owner `withdrawFees` |
| 创作者版税 5% | 0.000075 | 留在合约，等收款人 `withdrawRoyalties` |
| 卖家实得 | 0.0013875 | 当场 `call` 转走（0.0015 − 0.0000375 − 0.000075） |
| 悬空代管（B 对 #2） | 0.001 | `OFFER_B_HANGING`，故意留着不退 |
| **合约余额增量** | **0.0011125** | = 0.0000375 + 0.000075 + 0.001 |

脚本里这段由 L663-682 的四条断言保证：`feeGain === qFee`、`royaltyGain === qRoyalty`、`sellerGain === qProceeds`、三者之和 === 成交价。步骤 10（L860 附近）特意留了那笔悬空出价，就是为了让守恒校验的"代管项"不为 0 —— **如果代管项是 0，等式会退化，少验证一个维度**。

### 为什么脚本改成"增量口径"

`marketBalBaseline`（L464）和 `feesBaseline`（L465）在任何一笔交易之前快照。之后所有比较都取"链上当前值 − 基线"。

**踩过的坑（这条是踩得最实的）**：脚本最初直接用总额比对 —— `合约余额 == 四项之和`。本地每次新部署、合约零余额时完全正确；切到 Sepolia 复用那个跑过多轮的旧合约，`0x3FeEf...` 上本来就躺着历史残留（上一轮的悬空出价、累计手续费、累计版税），**总额比对必然对不上**，脚本一跑就炸，而且那个"不守恒"完全是假警报。改成增量口径后：本轮跑出来的钱和本轮账上的变化一一对应，历史存量单独打印（L873-875 `合约历史余额`），不参与断言。

配套规则：脚本读地址时若找不到部署产物，真实网络**直接报错退出，绝不静默重新部署**（`practice-offer.js` L17-20、L900-903），否则会在一套新合约上空跑一场，出来的数字毫无意义。

**另一个小坑**：校验卖家实得时必须把 gas 补回来（L654 `sellerGain = sellerBalAfter - sellerBalBefore + acceptGas`），否则"三方之和 == 成交价"在卖家付款的场景下永远差一点。

## 5. StaleOffer 机制

### 机制

- `Offer` 结构体：`SimpleMarket.sol` L230，字段 `targetOwner` 的含义写在 L233-234 —— 出价那一刻的持有者
- 写入时机：`makeOffer()` L527-529，**只在首次出价时记录**（`if (offer.amount == 0)`），后续加价不刷新
- 失效判据：`acceptOffer()` L630 要求 `ownerOf(tokenId) == msg.sender`（当前持有者），L633 又要求 `offer.targetOwner == msg.sender`（出价对象），两者缺一不可，否则 L636 `revert StaleOffer(msg.sender, offer.targetOwner)`
- 自定义错误：`StaleOffer(address currentOwner, address offerOwner)` L346

于是 NFT 转手后：

- 旧持有者来接受 → 他已不是持有者 → `NotTokenOwner`
- 新持有者来接受 → 他不是出价对象 → `StaleOffer`

测试 `SimpleMarket.test.js` L1519「【易主失效】NFT 转手后旧出价不可被接受，且买家能全额取回」完整覆盖：卖家把 #1 直接 `transferFrom` 给 other（不经过市场），然后 `other.acceptOffer(...)` 得 `StaleOffer`、`seller.acceptOffer(...)` 得 `NotTokenOwner`，最后 `buyer.withdrawOffer(...)` 断言 `changeEtherBalance(buyer, 0.5)` 且合约余额归零。

### 为什么这么设计：避免"新持有者被旧出价绑定"

出价是买家的**单方意思表示**，表达的是"我愿意从这个特定的人手里买"。NFT 一旦易主，交易对手就换人了 —— 新持有者当初根本没进入过这场议价，没道理被一笔他从未见过的出价绑定（一接受就等于强制成交）。同理，买家也不该因为 NFT 换了手，就被一个"当初没想卖给他的人"强制成交。

所以让旧出价**自动失效**，把决定权交还给双方：新持有者想卖，可以等新出价；买家想要，可以对新持有者重新出价。

（注：真实市场里也有让出价跟随 NFT 存活、由新持有者决定是否接受的方案，两种做法都有。本合约选了对买家更友好的"易主即失效"，取舍理由写在 `SimpleMarket.sol` L180-182。）

### 关键配套：取回通道永远畅通

失效不等于锁死。`withdrawOffer()`（L544）**不校验 `targetOwner`**，只读 `offer.amount`（L546-551），amount 非 0 就能全额取回。也就是说"易主即失效"这个设计的代价（买家的钱暂时被困在一笔无法成交的出价里）被压缩到零 —— 上面那条测试的最后两行断言就是在证明这件事。

前端侧也有配套：`getOffer()`（L751）同时返回 `amount` 和 `targetOwner`，前端只要把它和当前 `ownerOf` 比一下，就能在 UI 上把失效出价标灰，不用等用户点了才发现会 revert。

**踩过的坑**：`targetOwner` 只在 `amount == 0` 时写入（L528），这个条件不能省。如果每次加价都刷新，出价期间 NFT 易主、买家再加价，就会把 `targetOwner` 刷成新持有者 —— "易主即失效"的保护被绕过。反过来说，它带来的副作用是：出价期间易主后，买家**不能通过加价来"救活"这笔出价**，只能取回重出。这是刻意的取舍，不是 bug。

## 七、电梯陈述：三句话讲清这个项目

1. **它是什么**：一个 ETH 计价的 NFT 市场合约，同时支持"卖家挂单"和"买家出价"两条成交路径，两条路径共用同一份分账代码 `_settleSale()`，平台费 2.5% + EIP-2981 版税自动分账，202 个测试用例全绿，已部署 Sepolia。

2. **难在哪**：出价意味着合约要代管买家的钱，于是"怎么把钱还回去"成了核心安全问题 —— 我的解法是全链路 Pull Payment：成交只清被接受的那笔、落选者自取、退款失败转待领池绝不 revert，把"我能不能收到钱"和"别人的操作能不能成功"彻底解耦，宁可让用户多调一次 `withdraw`，也不让任何一个外部地址有卡死合约的能力。

3. **怎么证明它是对的**：五个恶意合约（`RejectingOfferBidder` / `ReenteringOfferBidder` / `RefundRejectingBuyer` / `EthRejectingReceiver` / `RoyaltyRejectingReceiver`）逐条打这些边界，重入被挡时断言的是 revert 数据本身的 `ReentrancyGuardReentrantCall` 选择器而不是"没成功"；最后用一条守恒等式 `合约余额 = 代管 + 待领池 + 平台费 + 版税` 收口，在 Sepolia 真实合约上跑完整流程后逐项对账 —— 每一分钱都能说清来路。
