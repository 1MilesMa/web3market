## 二、电梯陈述

### 30 秒版

> 我写了一个**授权式**的 NFT 市场合约——挂单时 NFT 不离开卖家钱包，只在成交瞬间由合约代转移。它支持**买家出价**，同一枚 NFT 可被多人同时出价、资金由合约托管，成交时统一走一套分账逻辑完成「平台费 → 版税 → 卖家」三方结算。所有对外转账一律走 **Pull Payment**，宁可把钱留在待领池，也绝不让一笔失败的退款卡死整个交易。最近还加了 **EIP-712 链下签名挂单**：卖家签名一分钱 gas 不花，买家带签名上链一次成交，成交 gas 还比传统路径省 40%。

### 3 分钟版

> 这个项目从零开始，包含四个合约：一个 ERC20、一个带版税的 ERC721，以及核心市场合约 `SimpleMarket`，外加一套 15 个恶意合约组成的攻击面测试集。
>
> 设计上我做了一个关键选择：**授权式而非托管式**。主流市场挂单时要把 NFT 转到市场合约里托管，我的做法是只记录价格、保留卖家的 `setApprovalForAll` 授权，成交时才由合约代转移。好处有两层——一是挂单和取消都省掉了 NFT 的物理转移；二是更重要的，合约本身不持有任何 NFT，**即使市场合约被攻破，也不会发生批量失窃**，风险敞口大幅收窄。
>
> 出价模块允许任意买家对同一枚 NFT 同时出价，资金按 `nft → tokenId → bidder` 分插托管，重复出价是**累加**语义（加价），要降价必须先取回再重出。卖家接受出价时，与一口价购买共用同一个 `_settleSale()`，保证分账算法只有一份实现，不会出现两条路径算钱不一致的经典 bug。
>
> 安全上我做了三件事：第一，四个涉及转账的函数加 `nonReentrant`，但 `makeOffer` 故意不加——因为它唯一的外部调用是 `ownerOf`，属于 `STATICCALL`，没有写入面，不存在重入路径，加锁反而是多余的 gas。第二，**拒绝批量退款**：卖家拒绝出价时，如果退款失败，我不让交易 revert，而是把钱转入待领池让对方自取——否则一个恶意买家只要部署一个拒收 ETH 的合约来出价，就能让卖家永远无法拒绝任何出价，这是典型的 DoS 攻击面。第三，用**资金守恒不变量**（合约余额 = 代管 + 待领池 + 平台费 + 版税）在每次演练都做校验，实测链上跑下来 0.0011125 ETH 完全对得上。
>
> 最后是验证：225 条测试全绿，`SimpleMarket` 语句/分支/函数/行覆盖率全部 100%；链上实跑两轮：出价流程 11 步、24 项校验全过（重入攻击、拒收 ETH 攻击都被正确挡下）；EIP-712 签名挂单 12 步全过，四道防重放防线——重放旧签名、改价后沿用旧 nonce、过期签名、紧急下架后使用旧签名——全部按预期拦截。

## 四、五个核心技术决策

### 决策 1：授权式挂单，而非转账托管

- **做法**：`listing` 只记录价格，NFT 留在卖家钱包；成交时合约凭 `setApprovalForAll` 授权代转移。
- **收益**：挂单与取消环节省掉两次 NFT 物理转移；合约不持有 NFT，被攻破也不会批量失窃。
- **代价**：成交时转移仍在链上进行，gas 与托管式相当；且**换合约就要重新授权**——每部署一次新市场，卖家都得重新 `setApprovalForAll`，这是授权式特有的运维成本。
- **一句话**：用一次性的授权成本，换掉长期的风险敞口。

### 决策 2：全量 Pull Payment，合约从不主动转账

- **做法**：平台费、版税、退回的出价款**一律先记账**，收款人主动 `withdraw*`。
- **收益**：把「转账成功」从交易的前置条件里拆出去，任何收款方的异常都不会阻塞主流程。这是整套合约最核心的工程决策。
- **代价**：收款人多一次交易和 gas；需要额外维护待领池账目。
- **一句话**：主动推送是把失败风险扛在自己身上，Pull Payment 是把风险交还给收款人。

### 决策 3：拒绝批量退款，宁可入待领池也不 revert

- **做法**：`rejectOffer` 单笔退款失败时**不 revert**，转入待领池。
- **收益**：堵死「恶意买家部署拒收合约出价 → 卖家无法拒绝」的 DoS 路径。
- **代价**：资金可能滞留待领池，需要链下提醒或前端展示待领余额。
- **一句话**：可用性优先于原子性——一笔退款失败，不该让卖家失去对商品的控制权。

### 决策 4：分账算法只保留一份（`_settleSale`）

- **做法**：`buy`（一口价）与 `acceptOffer`（接受出价）共用同一个 `_settleSale()`。
- **收益**：消除「两条路径算钱不一致」这一经典 bug 来源；改费率只改一处。
- **一句话**：钱的逻辑一旦复制，就一定会 divergent。

### 决策 5：`nonReentrant` 选择性加锁

- **做法**：4 个涉及 `CALL` 转 ETH 的函数加锁；`makeOffer` **不加锁**。
- **理由**：`makeOffer` 唯一的外部调用是 `ownerOf`，属于 `STATICCALL`，无写入面，不存在重入路径。
- **一句话**：锁是给写入路径的，不是给所有函数的装饰品——这是「知道为什么不加」和「全都加上求安心」的区别。

### 决策 6：EIP-712 链下签名挂单，把卖家的挂单 gas 归零

- **做法**：卖家离线签 `ListingIntent`（NFT + 价格 + nonce + deadline），买家带着签名调 `fulfillListing`，合约验签通过即完成「撮合 + 成交 + 分账」。
- **收益**：卖家的挂单、改价、下架全部在链下完成，**零 gas**；成交路径 gas 从 228,283 降到 135,600（省约 40%），省掉的是单独那笔挂单的 storage 写入。
- **代价**：签名必须自带防重放设计，否则一条签名能被无限次利用；紧急下架要发一笔 `incrementNonce()` 花 gas，换来的是「不必知道签名曾经发给过谁」。
- **一句话**：链下签名把「谁该为挂单付费」这件事，从卖家转移到了真正想成交的人身上。

---

### 决策 7：治理加固 —— 所有权两步转移 + 只挡开仓的紧急暂停

- **做法**：`Ownable` 换成 `Ownable2Step`（`transferOwnership` 后须新 owner 主动 `acceptOwnership` 才生效）；接入 `Pausable`，但只在**开仓类**入口加 `whenNotPaused` —— 挂单 / 改价 / 买入 / 出价 / 接受出价 / 签名成交，以及 NFT 铸造。
- **收益**：转错地址时新 owner 不确认就不会失控，`pendingOwner` 全程可查可覆盖；出事时能一键止血。
- **代价**：多一次确认交易；暂停期间开不了新仓（这是有意为之）。
- **关键取舍**：**撤单、取回出价、各类提现一律不加暂停修饰** —— 紧急暂停只能阻止新风险进来，绝不能把已经躺在合约里的钱冻住，否则「止血」就变成了「劫持」。
- **一句话**：暂停键要能停住新增风险，但停不住任何人的退出通道。

## 五、安全设计与攻击面覆盖

| 攻击面 | 防护手段 | 验证 |
|---|---|---|
| 重入 | 转账函数 `nonReentrant`；先改状态后转账 | 4 类重入载体（`ReenteringOwner` / `ReenteringFeeReceiver` / `ReenteringRoyaltyReceiver` / `ReenteringOfferBidder`）全部被挡下 |
| 拒收 ETH（DoS） | Pull Payment + 退款失败转待领池 | 5 类拒收载体（`EthRejectingReceiver` / `RefundRejectingBuyer` / `RoyaltyRejectingReceiver` / `RejectingOfferBidder` / `RejectingSeller`），链上实跑中确认交易不 revert、资金可后续领回 |
| 假 ERC721 接收器 | 遵循 safeTransfer 语义校验 | 恶意合约覆盖 |
| 权限越界 | 非 owner / 非卖家的调用路径测试 | 测试用例覆盖 |
| 资金错账 | 不变量「合约余额 = 代管 + 待领池 + 平台费 + 版税」每次校验 | 链上守恒通过（0.0011125 ETH） |
| 签名重放（EIP-712） | nonce 用后即焚 + `deadline` 过期 + `chainId`/合约地址域分隔 | 专项 20 条测试；链上主动发起 4 次重放攻击（原样重放 / 改价重签 / 过期签名 / 跳号后用旧签名），全部被 `InvalidNonce`、`SignatureExpired` 拦截 |

| 所有权转移事故 | `Ownable2Step` 两步确认（新 owner 需主动 `acceptOwnership`） | 测试覆盖（`pendingOwner` 断言 + 未确认前 owner 不变） |
| 紧急事件止血 | `Pausable` 只挡开仓类入口，撤单 / 取回出价 / 各类提现均不受影响 | 测试覆盖（暂停后撤单与提现仍可用） |

## 七、答辩 Q&A

**Q1：为什么不用现成的 OpenZeppelin 市场实现，要自己写？**
A：OZ 并没有官方的 marketplace 实现，市面上的成熟市场（OpenSea 等）是链下撮合 + 链上结算的混合架构。我做这个项目的目的是把「授权、版税、出价、资金托管」这几条链路亲手实现一遍并验证到 100% 覆盖，用现成库就失去练习意义了。安全基础设施（ERC721、ERC2981、ReentrancyGuard）我依然用的是 OpenZeppelin v5，没有重复造轮子。

**Q2：授权式真的比托管式省 gas 吗？**
A：准确说法是**挂单和取消**环节省——托管式挂单要把 NFT 转进市场、取消再转回，两次 ERC721 transfer；授权式只写 storage，取消更是只清 storage 还有 gas refund。成交环节两者相当，都要做一次转移。所以真正的收益是「降低挂单摩擦 + 收窄风险敞口」，不是「全面省 gas」——这点我在 README 里的表述也做了修正。

**Q3：`makeOffer` 不加重入锁，你确定安全吗？**
A：确定，因为重入的前提是外部调用能改状态。它唯一的外部调用是 `ownerOf`，编译后是 `STATICCALL`，协议层面禁止状态修改，没有重入路径。加锁反而多消耗 gas 和 storage。这个判断的依据是调用图分析，不是感觉。

**Q4：为什么宁可让钱留在待领池，也要拒绝批量退款？**
A：因为批量退款 + revert 会形成 DoS：任何人部署一个 `receive()` 直接 revert 的合约来出价，卖家一拒绝就整笔 revert，等于**卖家的商品被永久锁死**。Pull Payment 把「退款成功」从交易成功条件里摘掉，卖家一定能拒绝，钱则记账等待对方自取。代价是资金可能滞留，这由前端展示待领余额来缓解。

**Q5：重复出价是累加而不是覆盖，会不会有资金风险？**
A：累加语义下，买家想降价必须先 `withdrawOffer` 取回再重出，链上是两笔交易。风险点在两笔之间可能被卖家抢先 `acceptOffer` 接受旧高价——这是我们明确接受的取舍（用「先取回再重出」的显式操作换取语义简单），并在文档里写清。如果做成「允许降价」，就需要处理部分退款和并发接受，复杂度显著上升，对这个规模的项目不划算。

**Q6：EIP-2981 版税能在链上强制吗？**
A：**不能强制，这是标准本身的局限**。EIP-2981 只定义 `royaltyInfo()` 查询接口，要不要付、付多少由市场合约自觉。我的市场在 `_settleSale()` 里主动调用它并执行分账，所以在本市场内版税是强制的；但如果卖家绕过市场私下转账，版税就拿不到。这是整个行业的已知问题，不是实现缺陷——真正的链上强制需要 ERC721C 这类转移层拦截方案。

**Q7：平台费 owner 能随便改吗？**
A：有 `MAX_FEE_BPS = 1000`（10%）硬上限，改不到天上去。但 owner 在上限内确实可以单方面调高——这是当前实现的治理弱点。生产级做法应该是加 timelock（改动需延迟生效）或把 owner 交给多签，这也是我列的后续演进项之一。

**Q8：225 条测试、覆盖率 100%，是不是就没 bug 了？**
A：**不是**。覆盖率 100% 只说明每一行都被执行过，不说明每个状态组合都被验证。真正给信心的是另外三件事：不变量校验（资金守恒）、恶意合约攻击集（15 个攻击载体）、链上实跑（真实网络环境验证）。而且我还没有做形式化验证和专业审计——这两项才是上生产前的硬门槛。

**Q9：你怎么保证资金不会卡死在合约里？**
A：三层保障。第一，所有对外转账走 Pull Payment，钱永远有明确的 `withdraw` 出口；第二，退款失败不 revert，转待领池，出口依然存在；第三，不变量「合约余额 = 代管 + 待领池 + 平台费 + 版税」在每次演练都校验，链上实跑最终对账 0.0011125 ETH 完全吻合。

**Q10：你做静态安全分析了吗？Slither 结果怎么样？**
A：做了，而且过程本身就能说明问题。Windows 下 Slither 经 crytic-compile 解析 Hardhat 项目会卡死，我试了 6 种方式全部无产物，当时就如实归档为「未做」，没有伪造残缺报告。后来我换到 WSL2 Ubuntu 22.04 环境，绕开 Hardhat 解析层——只把 contracts 和 OpenZeppelin 复制进 ext4 目录，用 `--solc` 显式指定编译器、`--solc-remaps` 手工解析依赖——Slither 0.11.6 + solc 0.8.28 一次跑通。结果是 **47 条告警全部 INFO 级，零 Medium、零 High**。

**Q13：签名挂单最大的风险是什么？怎么防的？**
A：最大风险是**签名重放**——同一条签名被反复用来成交。我做了三层防护：一是 nonce 用后即焚，成交即 `listingNonces[seller]++`；二是 deadline 过期作废；三是 EIP-712 域分隔里带 `chainId` 与市场合约地址，主网签名拿到测试网、或拿到另一个市场合约一律失效。链上实跑时我主动发起了四次攻击——重放旧签名、改价后沿用旧 nonce、使用过期签名、卖家跳号后用旧签名，全部被 `InvalidNonce` / `SignatureExpired` 挡下，交易哈希都留在 README 里。

**Q14：签名挂单这么省 gas，为什么不干脆取代传统挂单？**
A：因为两者的**信任模型不同**。传统挂单是卖家主动把价格写进链上状态，任何前端都能直接读，订单簿天然公开、可聚合；签名挂单的价格只存在于签名里，链上读不到「这个卖家现在想卖多少」，必须自建链下渠道去传播和索引。所以我保留了两条路径并存：一口价 `listing` 走链上公开状态，签名挂单走省 gas 路径，卖家按场景自选——这也是 OpenSea 等真实市场的做法：链下订单簿 + 链上结算。
